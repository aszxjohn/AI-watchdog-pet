## Q1 —「包內勾選角色」和固定參數「加入池子」是不是同一個開關？

- **影響：** AD-12（池子組成）、AD-3（設定存哪）、AD-11（固定參數）
- **背景：** 你說過兩句話：「編輯頁上半部有『加入池子』」和「可以在包內勾選哪些角色進池子」。現在 spine 把它們當成兩個不同的開關，角色要兩個都開才會出現。

| 選項 | 結果 |
| --- | --- |
| A（建議）同一個開關：每個角色只有一個「加入池子」，在編輯頁或包管理頁勾的都是它 | 不會出現「一邊打開、另一邊還關著，角色就是不出來」的困惑 |
| B 兩個開關，兩個都開才進池子（現稿） | 兩個頁面各有一個勾選框，意思接近，容易搞混 |

## Q2 — 確認沙盒做法（AD-7）

- **影響：** AD-7，以及依賴它的 AD-16～AD-19（角色包 API、載入流程）
- **背景：** 這是研究時的建議，你當時沒反對，但沒有正式說採用。做法是四層防護：每包一個隔離的小頁面 → 角色程式只在背景執行緒跑 → 再用 SES 鎖住，只給舞台的 API → 只能用訊息跟舞台溝通，而且完全不能連網。審查發現一個必要條件：SES 要能動態執行程式碼，所以「沙盒內部」必須允許 `'unsafe-eval'`；這個允許只在沙盒裡，舞台本身的畫面不開。

| 選項 | 結果 |
| --- | --- |
| A（建議）採用四層做法，接受沙盒內開 `'unsafe-eval'`；寫程式前先做原型，原型不過再回來討論 | 防護最完整；隔離靠「背景執行緒＋SES＋不能連網」三層，不靠禁止動態執行 |
| B 採用，但不開 `'unsafe-eval'`：角色包要先經舞台提供的工具轉換才能安裝 | 等於把「角色包製作工具」提前到第一版，範圍變大 |
| C 拿掉 SES，只靠隔離頁面＋背景執行緒＋不能連網 | 少一層防護；包裡可以用系統時間與亂數，原本「不給現在時間」的規則擋不住 |

## Q3 — 匯出角色包時，能不能選擇附帶你的參數調整？（AD-13）

- **影響：** AD-13（匯出內容）；不影響 AD-11（調整仍只存在舞台設定）
- **背景：** Demo 有「一併匯出我的調整」選項。現稿是只匯出角色包本身。

| 選項 | 結果 |
| --- | --- |
| A（建議）可選附帶：調整另存成包裡的一個獨立檔，匯入時問對方要不要套用；角色包本身不被修改 | 跟 Demo 一樣；分享給別人時對方可以直接用你的設定 |
| B 第一版不附帶（現稿） | 比較簡單；對方要自己重新調 |

## Q4 — 名牌與標記（AD-9、AD-17）

- **影響：** AD-9（誰畫）、AD-16／AD-17（包拿到什麼、manifest 要不要宣告位置）、AD-22（推測狀態的顯示）
- **背景：** 你保留了「名牌與標記」，編輯頁也有「名牌與標記顯示」開關，但沒有規則說顯示什麼、誰畫。你也開放了「角色包可以讀 session 顯示名稱」，所以包有能力自己畫名牌。另外，有些狀態是推測出來的（例如「要你批准」可能其實是指令跑很久），要不要在畫面上看得出來。

**4a. 誰畫**

| 選項 | 結果 |
| --- | --- |
| A（建議）舞台統一畫在角色上方，位置由角色包在 manifest 宣告一個錨點；包不畫名牌，顯示名稱只拿來演出用；推測出來的狀態用不同樣式的標記 | 每個角色風格一致；「名牌與標記顯示」開關一個地方就能控制 |
| B 舞台預設畫，但包可以宣告「我自己畫」並接手 | 彈性大；各包風格不一，開關要靠包自己遵守 |
| C 全交給包畫 | 舞台最簡單；沒做名牌的包就沒有名牌 |

**4b. 名牌顯示什麼**

| 選項 | 結果 |
| --- | --- |
| A（建議）session 顯示名稱（例如專案或對話名） | 一眼看出哪隻代表哪個工作 |
| B 角色名 | 好認角色，但分不出是哪個 session |
| C 兩者都顯示 | 資訊最完整；名牌較長、較擠 |

## Q5 — 展示模式能不能指定角色？（AD-15）

- **影響：** AD-15（展示／示範）、AD-12（池子）
- **背景：** Demo 有兩種模式：示範＝8 個假 session 輪播狀態；展示＝畫面只留一隻，可以手動切狀態、換角色、重播進場，編輯頁的「在畫面上預覽」也靠它。現稿把兩者合成一個假轉接器、照池子隨機分配，所以展示模式沒辦法指定角色。這條（AD-15）的做法也沒有你的採用紀錄。

| 選項 | 結果 |
| --- | --- |
| A（建議）示範照池子分配；展示可以指定任何角色（包括沒勾進池子的），只對假 session 有效、不存檔、不佔池子名額；兩者都走同一套判斷與世界；編輯頁預覽用展示模式在畫布上演 | 跟真實行為一致，又能預覽任何角色 |
| B 展示也照池子隨機分配 | 最簡單；無法指定想看的角色，編輯頁不能預覽特定角色 |
| C 展示另寫一套，直接畫角色、不走偵測 | 可以任意控制；畫面行為可能跟真實不一樣（AD-15 原本要防的事） |

## Q6 — Copilot 要做哪一種？（AD-4）

- **影響：** AD-4（來源表）、命名慣例（來源代碼）、轉接器數量
- **背景：** 你說要支援「Cursor／GitHub Copilot」。研究時 Copilot 有兩種：Copilot CLI（有可讀的紀錄檔）和 VS Code 裡的 Copilot（沒有批准事件，唯讀來源還沒查到）。

| 選項 | 結果 |
| --- | --- |
| A（建議）第一版只做 Copilot CLI，VS Code 版延後 | 5 個轉接器，來源都已知 |
| B CLI 和 VS Code 都做，拆成 `copilot-cli`、`copilot-vscode` 兩個來源 | 要先查 VS Code 版的唯讀來源；它的「要你批准」只能靠推測 |

## Q7 — 角色包能不能影響自己角色的移動？（AD-10）

- **影響：** AD-10（世界歸舞台）、AD-16（舞台 API 多一個功能）
- **背景：** 你決定位置與移動歸舞台，又希望同一包的角色可以互相互動。如果包完全不能影響移動，「工作中的角色坐下」可能會一邊坐一邊被舞台拖著走。

| 選項 | 結果 |
| --- | --- |
| A（建議）包只能請自己的角色「停在原地／恢復遊走」和「轉向」，不能指定位置；你在編輯頁設的遊走偏好優先（設成不遊走就一定不動）；包看不到座標，靠「靠近／碰撞」事件知道誰在旁邊 | 同包互動做得到（例：坐下工作、轉身朝同伴開火），世界仍完全歸舞台 |
| B 包完全不能影響移動 | 最簡單；同包互動只能在原地演，動作與移動可能對不上 |
| C 包還能請自己的角色「走向同包某隻」 | 互動最豐富；舞台要多做路線與衝突處理 |

## Q8 — 包被停用、移除、更新後角色不見、或程式當掉時，畫面上已有的角色怎麼辦？（AD-19）

- **影響：** AD-12（分配）、AD-19（執行期生命週期）
- **背景：** 現稿只寫「當掉就改演佔位」，沒寫之後怎麼辦，也沒寫停用時已經在畫面上的角色怎麼辦。

| 選項 | 結果 |
| --- | --- |
| A（建議）停用、移除、取消勾選、更新後角色消失：立刻換成池子裡的其他角色（舊的離場、新的進場）；當掉：先演佔位並自動重啟，最多 3 次，還不行就當成停用處理，並在包管理頁顯示原因 | 畫面不會長期卡著佔位；短暫出錯不會換角色 |
| B 一律維持到該 session 結束，期間演佔位 | 不會突然換角色；停用的包可能還掛著佔位很久 |
| C 一當掉就立刻換角色 | 最單純；偶發錯誤也會讓角色被換掉 |

## Q9 — 點角色會發生什麼？app 從哪裡打開？（AD-14）

- **影響：** AD-14（穿透與點擊）、面板與視窗的入口
- **背景：** 現稿只寫「游標在角色上才接滑鼠」，沒寫接到滑鼠後做什麼；Linux 寫「選單改走系統匣」，等於預設有選單，但沒寫內容。Demo 有選單列、Dock 與角色右鍵選單。角色包本身仍然收不到滑鼠事件（你已決定）。

| 選項 | 結果 |
| --- | --- |
| A（建議）左鍵拖曳移動角色（放開後恢復遊走）；右鍵開選單（這個角色的編輯頁、管理 session、暫停／顯示）；app 入口放在 macOS 選單列與 Windows 系統匣，不顯示 Dock／工作列圖示 | 接近 Demo；不佔 Dock |
| B 同 A，但不能拖曳，只有右鍵選單 | 角色位置完全由舞台決定，比較單純 |
| C 同 A，但保留 Dock／工作列圖示 | 比較好找到 app；多一個圖示 |

## Q10 — 參數要不要能「換圖」？（AD-11）

- **影響：** AD-11（參數型別）、AD-13（manifest）
- **背景：** 現稿的參數型別只有開關、整數、數字、選項四種。Demo 還有「換圖」型別，例如換子彈的圖案。

| 選項 | 結果 |
| --- | --- |
| A（建議）加「換圖」型別，只能在包裡已宣告的圖裡挑 | 跟 Demo 一樣能換圖；不能用包外的圖檔，安全規則不變 |
| B 第一版只有四種（現稿） | 比較簡單；換圖要等下一版 |
